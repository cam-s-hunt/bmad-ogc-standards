## B. What each source contains and says about itself

### B1. NCOR PROV-to-BFO (source 1)

- **Contents [checked].** Three release files: `prov-bfo-directmappings.ttl` (552 lines; PROV-O to BFO), `prov-ro-directmappings.ttl` (RO), `prov-cco-directmappings.ttl` (CCO). `src/prov-mappings-edit.ttl` (editor's file with imports, development only), `src/build/artifacts/` (SSSOM CSV with 76 rows, entailed-mappings TTL, empty `unmapped-terms.csv`), `src/docs/Inconsistencies.md`, `Diagrams.md`, PROV canonical example instances, SPARQL queries, a Makefile and a GitHub workflow (not run). Only Turtle; no RDF/XML.
- **What it maps.** PROV-O, PROV-AQ, PROV-Dictionary, PROV-Links, PROV-Inverses and PROV-DC. README: "Every class and object property from PROV-O and its extensions is mapped to some class or object property from BFO, RO, or CCO." `unmapped-terms.csv` is empty [checked]. Method **[source]**: `rdfs:subClassOf`, `rdfs:subPropertyOf`, `owl:equivalentClass`, `owl:equivalentProperty`; SWRL rules and property chains for indirect relations; SKOS for commentary; each mapping carries `rdfs:comment` justifications and SSSOM-style `sssom:object_label`.
- **Axiom inventory [checked].** BFO file: 12 class mappings, 15 property mappings, 8 SWRL rules (all about `prov:atLocation`). CCO file: 33 annotated axioms, 1 `propertyChainAxiom` (`prov:hadPlan`), SWRL rules. RO file: 25 axioms, 1 chain. Examples: `prov:Activity owl:equivalentClass bfo:process`; `prov:Entity` subClassOf (independent continuant minus spatial region) or GDC or SDC; `prov:Agent` subClassOf (material entity and participates-in some Activity and bearer-of some (role realized in some Activity)); `prov:Plan` subClassOf GDC; `prov:Location` equivalent to site; `prov:InstantaneousEvent` equivalent to process boundary.
- **Encoding caveat [checked].** Every mapping is an `owl:Axiom` reification (annotatedSource/Property/Target) and the file contains **zero** plain triples such as `prov:used rdfs:subPropertyOf ...` (0 grep hits for `^prov:X rdfs:sub...`). Only OWLAPI-style tools (Protégé, ROBOT) reconstruct the axioms; the SSN-to-BFO team's own audit (`ncor-ssn-to-bfo/SSN-to-BFO/reports/ssn-vs-prov-comparison.md`, a partisan self-report) says RDFLib rejects two of the files and does not reconstruct the main axiom triples. I did not test this. Also, the release `prov-bfo-directmappings.ttl` on main uses `xsd:` and the default `:` prefix without declaring them (open issues #43/#44, filed 2026-10-06 by an outside user, no replies); the file at the tag v2025-01-19 additionally contains the invalid predicate `rdfs:comment:` (issue #40, fixed on main). So neither the tag nor main is a clean strict-Turtle file.
- **BFO / CCO versions.** BFO-2020 (ISO 21838-2) via `https://raw.githubusercontent.com/BFO-ontology/BFO-2020/release-2024-01-29/src/owl/bfo-core.ttl` **[source]**, `prov:wasDerivedFrom` in the file header. CCO: `v2.0-2024-11-06` merged **[source]** (in `prov-cco-directmappings.ttl`; the file also `owl:imports` the BFO mapping file). PROV-O 2013-04-30. All 17 CCO IDs used resolve in my CCO v2.2 copy and none is deprecated [checked].
- **CCO reuse.** Yes, in the separate `prov-cco` file: `prov:Agent` equivalentClass (cco Agent and agent-in some Activity); `prov:Person` and `prov:Organization` equivalent to the CCO classes; `prov:Plan`/`Bundle` subClassOf Information Content Entity; `prov:Start`/`End` equivalent to Process Beginning/Ending; properties to `has agent`, `is output of`, `has output`, `affects`, `is affected by`, etc.
- **Licence.** CC0 1.0 (repo LICENSE; `dc:license` in files). **Maintainer.** GitHub owner `NCOR-Organization` (NCOR = "The Ontology Research & Development Network", ncor-network.org); README and ontology IRIs still point at the old `BFO-Mappings` org, which no longer exists as a GitHub org (404) [checked]. Authors: Prudhomme, De Colle, Liebers, Sculley, Xie, Cohen, Beverley (CITATION.cff). 93 of the latest 100 commits are Tim Prudhomme's.
- **Activity / status.** Last commit 2025-08-04 (about 15 months before today); five tagged releases 2024-05 to 2025-01; 2 open issues, both filed 2026-10-06 and unanswered. **Status [source]:** the README presents the release files as "Use this file in production". The work is published and peer-reviewed: Prudhomme et al., "A semantic approach to mapping the Provenance Ontology to Basic Formal Ontology", Scientific Data 12, 282 (2025), doi 10.1038/s41597-025-04580-1; Zenodo archive 10.5281/zenodo.11338700 (I did not fetch the paper). No endorsement by W3C, BFO or CCO is claimed.

## C. Comparison

### C1. Relationship between SSN-to-BFO and the W3C module

- **Same authors? Partly overlapping community, different authorship.** W3C module: created by Simon Cox (`dcterms:creator`). SSN-to-BFO: commits by Alec Sculley; Danielle Limbaugh participates in its issues. Both Sculley and Limbaugh (Summit Knowledge Solutions) are listed contributors of the W3C WD, and they commented in W3C issue 429 (e.g. Limbaugh, 2026-06-02 to 07-03, proposing and justifying `cco:Sensor equivalentClass sosa:Sensor`, to which Cox replied "I can accept that"). Cox pinged `@avsculley` for input. **[checked]** (thread JSON in `w3c-ssn-2023-alignments/related-github-threads/`). Cox also writes of the Nature PROV-to-BFO paper "We aren't responsible for that work", saying he used it only for perspective (issue 401, 2025-11-23).
- **Influence, stated in the issue threads.** Cox (W3C issue 401, 2026-02-10): "Limbaugh provided a spreadsheet for an alignment of the 2017 edition of SSN to BFO/CCO. Mostly that was consistent with the conversations that we had already had. But from that I learned about cco:Cause ... Bittner drew my attention to cco:Planned Act". So the NCOR-side 2017 mapping fed the W3C module for at least Stimulus (Cause), Planned Act placement and hasResult ranges. W3C issue 429 and the NCOR issue tracker (#8) cross-link each other.
- **Does one supersede the other? No.** Neither the W3C TR/TTL nor the SSN-to-BFO README, docs or config mentions the other [checked by grep: no reference to `sosa-bfo.ttl` or the SDW alignments in SSN-to-BFO's README/docs/config; no mention of SSN-to-BFO in the W3C TR]; the link exists only in GitHub threads. They differ in scope (W3C: 33 simple axioms, section non-normative, a draft; NCOR: 100+ governed rows with restrictions and 'no mapping' decisions), in the SOSA edition (NCOR release = 2017; NCOR dev track = a 2026-07-22 snapshot of 2023; W3C = 2026-11-04 WD) and in design philosophy (W3C: "erred on the generalized side" per Cox, issue 398; NCOR: many rows deliberately unmapped or equivalent to class expressions to keep OWL DL consistency under HermiT/ELK). The thread shows the NCOR-side contributors' arguments partly adopted in discussion but **not** reflected in the final W3C TTL or SSN-to-BFO (see conflicts 1, 4, 5).
- **Status as at 2026-11-06 [inference]:** they are two independent, concurrently evolving mappings with an informal feedback loop through GitHub issues, not a lineage.

### C2. Same SOSA/SSN term mapped differently (W3C 2023 module vs NCOR; 2017 NCOR release shown where it differs)

1. **`sosa:Sensor`.** W3C TTL/7.1.3: `cco:Sensor rdfs:subClassOf sosa:Sensor` (CCO class is narrower), with the explanation "cco:Sensor is a subclass of cco:Material Entity, while sosa:Sensor may be non-material - e.g. a software agent". NCOR SOSA-next: `sosa:Sensor owl:equivalentClass cco:Sensor` (so sosa:Sensor becomes a material entity bearing a Sensor Function or Role). NCOR 2017 release: `sosa:Sensor` subClassOf (MaterialEntity and bearer-of some (RealizableEntity realized in some Observation) and agent-in some Observation), no use of `cco:Sensor`. The W3C issue 429 thread contains the argument for equivalence and Cox's acceptance on 2026-06-14, but the published module and text still say subclass and non-material.
2. **`sosa:Property`.** W3C: subClassOf (BFO quality **or** generically dependent continuant). NCOR SOSA-next and release: subClassOf (specifically dependent continuant **or** process profile) (release adds inherence restrictions for Observable/ActuatableProperty). The disjunctions overlap only in "quality as SDC"; W3C admits GDC (information) which NCOR excludes, NCOR admits process profiles which W3C excludes. The deleted `sosa-bco.ttl` had a third version (equivalentClass quality). Under SOSA-PROV (`Property subClassOf prov:Entity`) plus PROV-to-BFO the process-profile branch is lost [inference].
3. **`sosa:Observation`.** W3C: subClassOf `cco:Sensing Process` and subClassOf (hasResult only Descriptive ICE); and `cco:Act of Observation`, `Act of Measuring`, `Act of Prediction`, `Act of Estimation` are subclasses **of** `sosa:Observation`. NCOR 2017 release: `sosa:Observation` subClassOf (PlannedAct and has-process-part some (Act of Measuring **and** Act of Observation)), i.e. Act of Measuring/Observation are **parts of** an Observation, the reverse direction of W3C. NCOR SOSA-next: no direct mapping (deliberately removed; inherits Execution subClassOf (PlannedAct and prescribed-by some Procedure and has-agent some System)). Limbaugh's own comment in issue 429 (2026-07-03) says Act of Observation and sosa:Observation "overlap, and neither subsumes the other", yet the W3C module asserts subclass [source]. Consequence [inference]: with Observation under Sensing Process and Act of Observation under Observation, every CCO Act of Observation (defined as acquiring information "via the use of one or more senses", Limbaugh's own example: reading a memo) becomes a Sensing Process, i.e. realizes a Sensor Function or Role.
4. **`sosa:Sample`.** W3C: subClassOf independent continuant (and Sampling hasResult only independent continuant). NCOR SOSA-next: subClassOf (Continuant and isSampleOf some FOI), a deliberate weakening to admit statistical/data samples (the 429 thread proposed it for W3C too: "should be weakened to bfo:Continuant"; not adopted in the W3C TTL). NCOR 2017: equivalentClass (MaterialEntity and is-object-of some Sampling), narrower.
5. **`sosa:isSampleOf`.** W3C: subPropertyOf `cco:is successor of` (CCO domain and range: independent continuant). NCOR SOSA-next: no direct mapping, with a written reason. NCOR release v2026-07-18: a property chain `bfo:is_carrier_of o cco:represents` subproperty target; NCOR main has it deferred (property chains make the property non-simple, clashing with its functional declaration). So even NCOR's tag and main disagree here.
6. **`sosa:hasFeatureOfInterest`.** W3C: subPropertyOf `cco:has input` (domain process, range continuant). PROV route: subPropertyOf `prov:used`, which PROV-to-BFO maps to BFO `has participant` and PROV-to-CCO to `cco:affects`. NCOR SOSA-next: explicitly no mapping ("polymorphic subject relation"). NCOR 2017: only domain/range (Observation or Actuation or Sampling).
7. **`sosa:System`.** W3C: subClassOf independent continuant. NCOR: equivalentClass (MaterialEntity and implements some Procedure). W3C text keeps software and human systems possible; NCOR commits to materiality.

Agreements: `sosa:Procedure` subClassOf `cco:ont00000965` (Prescriptive ICE) in W3C and SOSA-next (the 2017 NCOR version says "Directive ICE and prescribes some Process", where Directive ICE is a CCO altLabel of the same class); `hasResult` subPropertyOf `cco:has output`; `usedProcedure` subPropertyOf `cco:prescribed by`; `Stimulus` under `cco:Cause` (NCOR adds "is cause of some Observation"); `Deployment` under `cco:Planned Act`; `wasOriginatedBy` to `caused by`.

### C3. Consistency with CCO's own treatment of sensors, observations and measurement

All checked against `docs/references/git/commoncoreontology-commoncoreontologies/src/cco-merged/CommonCoreOntologiesMerged.ttl` (v2.2) and `ontologies/alignment-evidence/cco-issue-848.json`, `-857.json`, plus CCO discussion 860.

- CCO v2.2 (after the March 2026 refactor, issue 848, closed 2026-03-31): `Sensor` ≡ material entity and bearer-of some (Sensor Function or Sensor Role); `Sensing Process` ≡ process and realizes some (Sensor Function or Sensor Role); `Sensor Platform` ≡ material entity and bearer-of some (Sensor Deployment Artifact Function or Sensor Platform Role). `Act of Observation` = a Planned Act "of acquiring information from a source via the use of one or more senses"; `Act of Measuring` = Planned Act determining extent/quantity "relative to some standard", with no output axiom. `Actuator` = a Transducer "designed to convert some control signal into mechanical motion". `Planned Act` ≡ Act that realizes a disposition or role concretizing a Prescriptive ICE (agent causative). `has output`/`has input` have process domain and non-spatial continuant range. `Cause` ≡ process that is cause of some process.
- Consistent with the NCOR SOSA-next choice for Sensor (equivalence) and, by construction, with the W3C subclass direction (any CCO sensor is a sosa:Sensor). The W3C text "sosa:Sensor may be non-material" conflicts with CCO's own materiality only if sosa:Sensor is declared equivalent; W3C avoids that by the one-way axiom [inference].
- CCO has no observation concept equal to `sosa:Observation`. CCO issue 857 (opened by Cox, closed 2026-04-06) asks that Sensor's definition include converting stimulus to a signal; Alan Ruttenberg replies the action is on the sensing role/function, "Not all sensors produce information. Signal isn't defined in CCO"; Cox's follow-up moved to discussion 860 (open, 1 comment) proposing to axiomatize Planned Act subclasses by output (`has output some Information Content Entity` for Observation, Measuring, Prediction, ...). In the TTL W3C already encodes the idea as `Observation ⊑ ∀hasResult.Descriptive ICE`. The CCO side has not adopted it.
- `Actuator`: the W3C module comments "CCO Actuator is for mechanical motion" and also puts `cco:Control System` under `sosa:Actuator`. NCOR SOSA-next drops CCO from Actuator (subClassOf material entity only) deliberately; Limbaugh's dot points in issue 429 keep `cco:Transducer` unmapped (the 2023 edition broadens Sensor/Actuator to social and virtual cases that convert no energy).
- `Planned Act` requires an Agent that is causatively active; the thread (Limbaugh, 2026-07-03) notes that an unattended weather station "strains the notion of agency". NCOR SOSA-next nonetheless asserts `Execution ⊑ PlannedAct ∩ has_agent some System` where `has agent` has range cco:Agent, so every System in an execution would be a cco:Agent [inference from the CCO `has agent` range]. The W3C TTL intended the same placement for Execution but the typo disables it.
- CCO property typing makes `sosa:hasFeatureOfInterest ⊑ cco:has input` and `hasResult ⊑ cco:has output` assert that a FOI/result is a (non-spatial) continuant [checked from the CCO range axioms]. That excludes occurrents as FOIs under the W3C mapping while BFO-level `sosa:FeatureOfInterest ⊑ BFO entity` allows them [inference].

### C4. Composed route SOSA-PROV + PROV-to-BFO/CCO (PROV-to-BFO's README says this is "derivable" from the SOSA-PROV mapping; `src/imports/SSN/README.md`)

NCOR issue #16 ("SOSA-PROVO-BFO alignment", asking whether the three alignments fit together) is unanswered. Reading the axioms, with no reasoner run **[inference]**:

- `sosa:hasFeatureOfInterest ⊑ prov:used ⊑ cco:affects` (PROV-CCO): observing a feature would imply the observation affects it; PROV-BFO gives `has participant`, which is milder.
- `sosa:madeBySystem ⊑ prov:wasAssociatedWith ⊑ cco:has agent`: every System in `madeBySystem` becomes a cco:Agent (matches NCOR-next's choice `madeBySystem ⊑ cco:has_agent`).
- `sosa:Property ⊑ prov:Entity` and `prov:Entity ⊑ continuant (non-spatial-region)`: removes NCOR's process-profile option for Property, and `sosa:FeatureOfInterest ⊑ prov:Entity` forces every FOI to be a continuant (NCOR-next keeps `bfo:Entity`).
- `sosa:isSampleOf ⊑ prov:wasDerivedFrom ⊑ RO causally influenced by` (PROV-RO only; PROV-BFO and PROV-CCO do not map `wasDerivedFrom`); versus W3C `is successor of`, which needs independent continuants on both sides and so excludes data samples.
- `sosa:Asset`/`System` ⊑ (`prov:Agent` or `prov:Entity`), and PROV-BFO puts `prov:Agent` under material entity (the PROV-BFO comment says `prov:SoftwareAgent` is a material entity because it is "running software" on a particular computer). This agrees with NCOR's material System but not with the W3C BFO module's "System may be non-material".
- The deleted W3C `bfo-prov.ttl` (Entity ≡ independent continuant) disagrees with PROV-to-BFO (Entity ⊑ IC-minus-SR or GDC or SDC).

## E. Recommendation and caveats

**What the sources say vs what I infer is labelled as above. This is my inference, not a source statement.**

Decision constraints: (1) the CS API cites the 2017 SOSA/SSN, so 2017 coverage matters; (2) a target standard may need software/virtual systems; (3) tooling: OGC people will likely use RDF/SHACL tooling, not only OWLAPI; (4) pinnability.

1. **SOSA/SSN to BFO/CCO.** Use **NCOR SSN-to-BFO tag v2026-07-18 (commit 221c65ab27b59ae701f2ed73a98cb9e79d77b750; asset sha256 69d68e4d...9b8be)** as the working reference for the 2017 terms the CS API uses (Sensor, Actuator, Platform, System, Observation, Actuation, Sampling, Sample, FOI, ObservableProperty, ActuatableProperty, Procedure, Result, Deployment, Stimulus). It is the only source mapping all of them, with justifications, a pinned CCO (2024-11-06), a checksum and an exact commit. Do **not** treat it as an authority: single-team maintained, self-labelled "authoritative", persistent IRIs (`sks.ai`) not verifiably dereferenceable, and it differs from `main` (hasSample/isSampleOf rows). Use the **W3C `sosa-bfo.ttl` (gh-pages commit 9ab7f8f440612a6605c90a10af35429db25125cf) and WD section 7.1.3** as the OGC/W3C-side reference for direction and vocabulary alignment, citing it only as non-normative draft material. Record the typo (`rdfs:subClassOF`) and the one-way Sensor/Actuator/Platform direction when quoting it. Do not rely on `http://www.w3.org/ns/sosa/bfo` (it serves `sosa.ttl`).
2. **PROV-O to BFO.** Use **NCOR PROV-to-BFO `main` at `c60847a4b838d25972d899731c0f6bb83716181d`**, not the tag v2025-01-19 (the tag has invalid Turtle `rdfs:comment:`; main lacks `xsd:`/default prefix declarations, issues #43/#44, so neither loads cleanly in a strict parser). It has a peer-reviewed paper, CC0, and the only complete PROV-O coverage. To use its mappings in RDF tooling, someone must reconstruct the axioms with an OWLAPI-based tool and publish plain triples (not tested). For `prov:wasDerivedFrom` there is only the RO file.
3. **CCO and BFO pins.** Pin CCO **v2.2** (commit `0bc7d33e1bc09fd4693366119ab4e03cb0340042`, already pinned at `docs/references/git/commoncoreontology-commoncoreontologies/`) and BFO-2020 (ISO 21838-2); all CCO IRIs used by the W3C module, SSN-to-BFO (both tracks) and PROV-CCO exist in v2.2 and none is deprecated [checked], but labels/definitions between 2024-11-06 and v2.2 changed (Sensor refactor, Prescriptive/Descriptive naming) and the NCOR current track targets 2024-11-06. CCO 3.0 (IRI scheme change, expected end of 2026 per the earlier manifest) will break all `ont000*` mappings. Do not import unversioned `https://www.commoncoreontologies.org/CommonCoreOntologiesMerged` (it 301s to a moving `develop` branch file).
4. **Do not pick one mapping as normative for a target standard.** Keep the standard's own concepts grounded by explicit, versioned mapping tables (SKOS-style closeMatch/related or your own axioms) that cite these sources, because the two SOSA-BFO mappings contradict each other on core terms (C2), the W3C one is a draft, and the NCOR 2023 track is not released.

**What is missing (for a standard that covers software or virtual systems) [inference]:**
- Software/virtual systems. NCOR makes System, Sensor and Actuator material entities; PROV-to-BFO makes `prov:Agent` (including `SoftwareAgent`) a material entity; W3C makes System an independent continuant but its text says a Sensor may be a software agent. A BFO-style treatment of software as an information content entity (or its executions as processes) is covered by none of them. This is the central gap for a standard that models autonomous behaviour.
- Anything about state machines, behaviour trees, plans-as-executable-structures, commands/tasking beyond `sosa:Actuation` (CS API Command and ControlStream are only in the WD's non-axiomatic 7.3.1 table; NCOR-2023 maps ActuationCollection but W3C-BFO does not).
- The 2023 terms the CS API 7.3.1 relies on (`observedProperty`, `actsOnProperty`, `hasMember`, `isSampleOfUltimateFOI`, `hasUltimateFeatureOfInterest`) have no BFO/CCO property mapping in either source (NCOR gives rationale: no mapping).
- Deprecated 2023 terms (ObservableProperty, ActuatableProperty, Result) are mapped only by NCOR's 2017 track.
- Observation results, units and OMS (`sosa-oms`) and time properties (`phenomenonTime`, `resultTime`) are mapped only partially (NCOR phenomenonTime/occupies temporal region in the 2017 track, NCOR-2023 `phenomenonTime` range TemporalRegion).
- No reasoning evidence for the W3C module (no reasoner statement); NCOR reports HermiT/ELK checks on its own products (reports; I did not re-run). Nobody has verified the composed SOSA-PROV + PROV-to-BFO + SOSA-BFO stack (NCOR issue #16, unanswered).

**Caveats.** (a) All opinions on correctness are from reading; none of the TTL files was loaded in a reasoner. (b) SSN-to-BFO's reports are largely machine-generated and self-assessed; I used them only for pointers, and everything quoted in C and D was re-read from the workbooks/TTL. (c) The current-track release workbook differs from main in two rows (hasSample, isSampleOf); D1 for NCOR-cur uses the release workbook (the other 107 rows are identical to main). (d) The W3C edition will keep changing (518 commits in 3.5 months); pin the commit, not the URL.
